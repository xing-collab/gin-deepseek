# 角色卡规则与应用端 Agent：现状分析与职责对比

## 1. 结论

角色卡规则可以应用到应用端 Agent，而且本项目已经具备一个最小可用的实现：应用负责角色状态和工具执行，模型负责根据当前状态生成回复。

当前链路如下：

```text
用户输入
  -> Character.Update(input)              应用更新角色状态
  -> Character.BuildSystemPrompt()        应用组装当前角色规则
  -> LLM                                  模型生成回复或请求工具
  -> StreamChanWithTools                   应用执行工具并回传结果
  -> LLM                                  模型继续生成，直到不再调用工具
  -> history                              应用保存最终对话
```

因此，当前实现可以称为“带角色状态机的轻量应用端 Agent”。它已经超出单次 LLM 问答，但还不具备完整生产级 Agent 所需的权限控制、执行预算、输出校验和会话隔离。

## 2. 当前代码如何落地角色卡

### 2.1 角色卡数据

`config/priestess.json` 保存角色身份、人格、认知方式、语言风格、状态描述、数值修正、触发器、行为规则和经典台词等数据。

`config/character.go` 使用 `CharacterCard` 映射 JSON，并通过 `Character` 保存运行时状态：

- `Base`：基础模式，例如 `normal`、`architect`。
- `Relationship`：当前关系状态。
- `Attachment`：情感连接强度。
- `Obsession`：执念强度。
- `RationalIntegrity`：理性完整性。
- `Event`：当前事件状态，例如 `crisis`。
- `Expression`：表达异常状态，例如 `glitch`。

这些值由 Go 程序维护，不依赖模型在每轮自行猜测，因此状态转换具有可测试性和可重复性。

### 2.2 状态更新

`Character.Update` 对用户输入进行关键词匹配，然后：

1. 累加情感连接、执念和理性修正值。
2. 对数值执行 `0..100` 限制。
3. 按触发器优先级更新基础、关系和事件状态。
4. 根据“高执念 + 低理性”组合条件决定是否进入 `glitch`。
5. 未命中触发器时，让部分数值缓慢回归稳态。

这部分属于应用端状态机，而不是提示词工程。

### 2.3 动态 system prompt

`Character.BuildSystemPrompt` 将以下内容按层次写入当前 system prompt：

- 身份、世界观和核心人格。
- 价值层级和决策规则。
- 当前多维状态及状态说明。
- 行为、回复和表达规则。
- 经典台词风格参考。

`LLM.snapshot` 每轮使用最新 prompt 构造：

```text
[当前 system prompt] + [历史 user/assistant 消息] + [本轮 user 消息]
```

因此，`Character.Update` 产生的新状态可以在下一次模型请求中立即生效，不会被第一轮 system 消息固定住。

### 2.4 Agent Loop 与工具调用

`InvokeWithTools` 和 `StreamChanWithTools` 已经实现最基础的 Agent Loop：

1. 模型读取上下文和工具声明。
2. 模型决定是否返回 `tool_calls`。
3. 应用解析参数并调用 handler。
4. 应用把工具结果作为 `role: tool` 消息回传。
5. 重复请求，直到模型给出最终回复。

目前工具只有时间和日期，风险较低；如果增加文件、数据库、网络请求或外部操作工具，需要额外的权限层。

## 3. 角色卡与应用端 Agent 的职责对比

| 规则或能力 | 适合 system prompt | 应用端必须处理 | 当前状态 |
| --- | --- | --- | --- |
| 身份、人格、语气 | 是 | 否 | 已实现 |
| 词汇偏好、经典台词 | 是 | 可选输出检查 | 已实现为 prompt |
| 当前情绪描述 | 是 | 状态值必须由应用维护 | 已实现 |
| 状态转换 | 否 | 是 | 已实现为关键词状态机 |
| 数值累加、阈值、优先级 | 否 | 是 | 已实现 |
| 工具选择 | 模型可建议 | 应用决定是否允许执行 | 部分实现 |
| 工具参数校验 | 否 | 是 | 只有 JSON 解析 |
| 最大工具调用轮数 | 否 | 是 | 未实现 |
| 用户授权与危险操作确认 | 否 | 是 | 未实现 |
| 会话记忆 | 可向模型提供 | 应用负责存储与裁剪 | 已实现内存短期记忆 |
| 多用户状态隔离 | 否 | 是 | CLI 单会话可用，服务端未实现 |
| 禁词硬约束 | prompt 只能引导 | 严格要求时需输出校验 | 当前主要依赖 prompt |
| Prompt Injection 防护 | 否 | 是 | 未实现完整防护 |
| 日志、审计、执行追踪 | 否 | 是 | 未实现 |

## 4. 三类规则的推荐落点

### 4.1 必须由应用强制执行

以下规则不能仅写进角色卡 prompt：

- 状态转换、数值范围和优先级。
- 工具白名单、参数 Schema 和调用次数上限。
- 用户身份、权限、授权确认和资源边界。
- 超时、取消、重试和执行预算。
- 文件、数据库、支付、消息发送等副作用操作的审批。
- 会话隔离、状态持久化和审计日志。

应用端规则是确定性约束；即使模型忽略角色设定，这些约束也必须继续生效。

### 4.2 适合交给模型表达

以下规则主要影响自然语言，可以通过动态 system prompt 实现：

- 人格、称呼、语气和语言密度。
- 世界观、关系设定和认知方式。
- 当前状态下应表现出的情绪。
- 词汇倾向、表达禁忌和台词风格。

这些规则是软约束。模型可能偶尔偏离；如果业务要求严格，就要在输出后增加验证和重写流程。

### 4.3 适合混合处理

“重大决定先分析候选方案”“危机时提高某个目标的权重”等规则需要两层实现：

1. 应用计算状态、权限和不可越过的边界。
2. 模型在这些边界内解释、规划或生成符合角色风格的表达。

角色卡不应成为授权来源。例如，卡片中的“无需征得许可、立即执行”只能影响剧情台词，不能授权 Agent 调用具有真实副作用的工具。

## 5. 当前实现与生产级应用端 Agent 对比

| 维度 | 当前实现 | 生产级建议 |
| --- | --- | --- |
| 编排位置 | `main.go` 串联各模块 | 提取独立 `Agent` 服务 |
| 状态识别 | `strings.Contains` 关键词 | 规则 + 意图分类 + 置信度校验 |
| 状态存储 | 进程内 `Character` | 按用户/会话持久化 |
| 对话记忆 | 进程内短期 history | 会话存储、摘要和检索记忆 |
| 工具循环 | 循环直到没有 tool call | 增加 `MaxSteps`、超时和取消 |
| 工具安全 | handler 直接执行 | 白名单、Schema、授权和审计 |
| 输出约束 | 依赖 system prompt | 输出验证、敏感规则检查、必要时重写 |
| 并发模型 | CLI 串行单用户 | 每会话独立状态，避免共享可变对象 |
| 可观测性 | 终端输出 | trace、状态转换日志、工具调用记录 |
| 测试 | 状态机和 HTTP 行为测试 | 增加 Agent 回归集和安全用例 |

## 6. 当前方案的主要风险

### 6.1 关键词误触发

当前使用子串匹配，可能无法区分否定、引用、假设和真实意图。例如用户讨论“电影中的死亡”也可能进入危机状态。

推荐先生成结构化意图，再由应用校验：

```json
{
  "intent": "doctor_danger",
  "confidence": 0.91,
  "evidence": "用户明确描述当前危险"
}
```

低置信度不切换高风险状态；最终状态转换仍由应用完成。

### 6.2 工具循环无执行上限

当前循环会持续到模型停止调用工具。应增加最大步数、总耗时和取消信号，避免异常模型响应造成无限循环或成本失控。

### 6.3 角色规则与安全规则混合

角色卡中可能存在激进的剧情决策规则。这些内容不能覆盖应用安全策略。建议优先级固定为：

```text
平台与法律约束
  > 应用安全和用户授权
  > Agent 工具策略
  > 任务目标
  > 角色卡人格与表达规则
```

### 6.4 多用户状态串扰

`Character`、`LLM.systemPrompt` 和 `LLM.history` 都包含可变状态。当前 CLI 串行使用没有问题；改造成 HTTP 服务后，不能把同一个实例作为所有用户共享的全局单例。

每个会话至少需要独立的：

- `CharacterState`
- 对话历史
- 当前 system prompt
- 工具执行预算
- 用户权限上下文

## 7. 推荐的应用端 Agent 结构

可以把 `main.go` 中的编排逻辑提取为独立类型：

```go
type Agent struct {
    LLM       *config.LLM
    Character *config.Character
    Tools     []config.Tool
    Handler   ToolHandler
    MaxSteps  int
}

func (a *Agent) Run(ctx context.Context, input string) (<-chan config.StreamDelta, <-chan error) {
    // 1. 输入安全检查和意图识别
    // 2. 应用端更新角色状态
    // 3. 构建动态 system prompt
    // 4. 在 MaxSteps 和 ctx 约束下执行工具循环
    // 5. 校验最终输出并保存状态
}
```

推荐请求流程：

```text
Input
  -> Input Policy
  -> Intent / Trigger Evaluation
  -> Character State Transition
  -> Dynamic System Prompt
  -> LLM Decision
       -> no tool: Output Validation -> Response
       -> tool: Tool Policy -> Authorization -> Execute
                                      -> Observation -> LLM Decision
```

## 8. 建议的落地顺序

1. 将 CLI 编排提取为独立 `Agent` 类型，但暂时保持现有行为。
2. 给工具循环增加 `context.Context`、`MaxSteps` 和超时。
3. 定义统一的工具注册结构，包含名称、Schema、风险等级和 handler。
4. 为有副作用的工具增加显式授权回调。
5. 将角色状态和历史按 session 隔离。
6. 增加状态转换、Prompt Injection、无限工具循环和权限绕过测试。
7. 再考虑用语义分类替换部分关键词规则。

## 9. 判断标准

当系统同时满足以下条件时，可以认为它是可靠的应用端角色 Agent：

- 角色状态由应用维护，而不是完全依赖模型自述。
- 每轮都将最新状态传给模型。
- 工具由应用执行，模型只有建议权，没有直接执行权。
- 权限、安全和资源边界独立于角色卡。
- 工具循环存在步数、时间和成本上限。
- 每个用户或会话拥有隔离的角色状态与记忆。
- 状态变化、工具调用和最终结果可测试、可追踪。

当前项目已经满足前面三项，并具备清晰的继续演进路径。
